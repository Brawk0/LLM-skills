# Именование и трассируемость прошивок LiDAR

## Назначение

Этот навык задаёт единый способ:

- применять корпоративное обозначение `BM/BF/MF/MP/FP/X`;
- использовать общее название изделия `R120M`, а линии FPGA разделять полем `BF` по ФИЗИЧЕСКОЙ ПЛАТЕ: `R120M.BF1` = старая плата `R120_M-1.1.0`, `R120M.BF2` = новая плата `R120M.BM2BF1X1`;
- однозначно связывать выданный `.fs`, `.bin` или `.hex` с исходным Git-коммитом;
- проверять точный образ по SHA-256 и, для Gowin, по `UserCode`;
- не выдавать грязную рабочую копию за воспроизводимую боевую прошивку.

Канонический репозиторий: `https://github.com/ak-tech-electronics/ToF-LIDAR-FPGA`.

## Локальные источники правил

Правила совместимости взяты из локального Obsidian:

- `Работа/Лидар/Протокол/Версирование/Версирование.md`;
- `Работа/Лидар/Протокол/Версирование/Примеры формирования названия при версировании.md`;
- старый журнал `Работа/Лидар/Протокол/Версирование/LDR2.M-BF1MF1FS1/Firmware_FPGA_log.txt`.

Каноническая форма задаётся актуальными заметками Obsidian: после названия изделия ставится точка, затем все поля совместимости и `X` записываются слитно. Подчёркивания и отдельные суффиксы типа прошивки не используются.

Смысл полей:

| Поле | Совместимость |
|---|---|
| `BM` | плата ↔ MCU |
| `BF` | плата ↔ FPGA |
| `MF` | MCU ↔ FPGA |
| `MP` | MCU ↔ PC |
| `FP` | FPGA ↔ PC |
| `X` | независимая внутренняя итерация конкретной прошивки |

`X` у MCU и FPGA независимы. Нельзя переносить значение `X` из имени MCU в имя FPGA автоматически. `BF` кодирует ФИЗИЧЕСКУЮ ПЛАТУ (электрический стык плата–FPGA), а не измеритель времени; измеритель — следствие платы.

## Постоянные боевые ветки

| Поле | Физическая плата | Что на плате | Боевой Git branch | Шаблон логического имени FPGA | Сборочная цель |
|---|---|---|---|---|---|
| `BF1` | `R120_M-1.1.0` (старая, проверена в железе) | только `2×TDC7201` | `R120M.BF1` | `R120M.BF1MF…FP…X…` | LDR_20K, top `R120_M_1_1_0_brd_ifm` (`20k/LDR_20K/build_gowin.tcl`) |
| `BF2` | `R120M.BM2BF1X1` (новая) | `LTDC-X3` + `2×TDC7201` + W5500; LTDC запущен, тракт SPI MSOP отлажен через X14 | `R120M.BF2` | `R120M.BF2MF…FP…X…` | top `R120M_ltdc_msop_brd_ifm` / `R120M_BM2BF1X1_brd_ifm` |

Новая плата `R120M.BM2BF1X1` несёт ОБА измерителя (LTDC и TDC7201), запускаемых
отдельными прошивками. По решению пользователя (21.07.2026) поле `BF` при этом
НЕ множится: новая плата остаётся `BF2`, а измеритель выбирается веткой:

- `R120M.BF2` — боевая LTDC-линия новой платы;
- `R120M.BF2_TDC7201` — вариантная ветка TDC7201 на той же плате (ответвлена от
  `R120M.BF2`, наследует базу BM2BF1X1: командный SPI-slave на пинах SSPI
  `use_sspi_as_gpio` и `HYSTERESIS=HIGH` на входе энкодера; top `R120M_BM2BF1X1_brd_ifm`).

Это вариантная ветка в смысле раздела «Экспериментальные прошивки ведутся
ответвлениями от боевой ветки платы», а не отдельная боевая `BF`-линия: обе
прошивки собираются под одну физическую плату `BM2BF1X1` (`BF2`). Значение `BF3`
НЕ вводится.

У плат разная разводка FPGA-пинов: битстрим одной платы на другой НЕ запускается (подтверждено 16.07.2026 — образ `R120M_BM2BF1X1` на `R120_M-1.1.0` мёртв). Перед сборкой сверять плату стенда с топом/CST, а не только ветку.

Исторический рубеж новой платы (BF2) — коммит `9a7bd23e02299a844c59e74d04649a7b9b31d8a9`: тракт `2×TDC7201` и MSOP-кадры проверены на `R120M.BM2BF1X1`. Линия старой платы (BF1) продолжается коммитами проекта LDR_20K; вершина, проверенная железом 16.07.2026, — `c7612a07` (на неё указывает `R120M.BF1`). Ветка `R120LD` — отдельные работы (m20k/BDSP2), в боевые линии не входит.

Боевой FPGA-branch состоит из имени изделия и зафиксированного поля `BF`. Поля `BM/MF/MP/FP/X`, Git hash, image hash и статус в имя branch не входят.

Полное логическое имя назначается конкретному выпуску после определения его совместимости. Поэтому одна и та же ветка последовательно содержит коммиты и сборки с разными значениями `MF`, `FP` и `X`, но с одним значением `BF`.

Не собирать официальный образ `BF1` из ветки `R120M.BF2` и образ `BF2` из ветки `R120M.BF1`.

## Логическое имя

FPGA:

```text
<модель>.BF<номер>MF<номер>FP<номер>X<номер>
```

MCU:

```text
<модель>.BM<номер>MF<номер>MP<номер>X<номер>
```

Точка отделяет модель от версии. Поля после точки идут слитно. Тип прошивки определяется набором полей:

- `BF/MF/FP/X` — FPGA;
- `BM/MF/MP/X` — MCU.

Не добавлять отдельные суффиксы `fpga` и `mcu`. Не принимать старые имена с подчёркиваниями как канонические.

Имя изделия вместе с полем `BF` определяет ожидаемую боевую ветку FPGA:

```text
R120M.BF1MF<номер>FP<номер>X<номер> -> branch R120M.BF1 -> плата R120_M-1.1.0 (TDC7201)
R120M.BF2MF<номер>FP<номер>X<номер> -> branch R120M.BF2 -> плата R120M.BM2BF1X1 (LTDC + TDC7201)
```

Значения `MF`, `FP` и `X` зависят от конкретного выпуска. Переход `X1 → X2` означает новую внутреннюю итерацию в рамках той же линии совместимости. Переход на другую физическую плату означает смену `BF`, и для новой линии `X` начинается с `X1`.

Экспериментальные прошивки ведутся ответвлениями от боевой ветки платы (например, `R120M.BF1_enc_edge_fire` — выстрел по фронту энкодера без ФАПЧ, ответвление от `R120M.BF1`); их коммиты в боевую ветку не вливаются без явного решения пользователя.

Выпуск из вариантной ветки использует обычную схему логического имени своей `BF`-линии; счётчик `X` вариантной прошивки независим от боевой линии (первый выпуск варианта — `X1`). Упаковка идёт с `-AllowOtherBranch` (факт ветки пишется в manifest), а на сервере файлы кладутся в подпапку с именем вариантной ветки, чтобы не смешиваться с боевой линией (прецеденты: `R120M_enc_edge_fire`, `R120M.BF2_TDC7201`). Первый выпуск TDC7201-варианта новой платы — `R120M.BF2MF5FP1X1` (git `54484c58`, MF5 = командный SPI МК→ПЛИС на пинах SSPI, FP1 = MSOP).

Раскладка папок на сервере повторяет РОДОСЛОВНУЮ веток, а не список имён.
Ответвление от вариантной ветки кладётся ВНУТРЬ папки своего родителя, а не
рядом с ней:

```text
Тестовые прошивки/
  R120M.BF2_echo_mode/                     <- вариант боевой линии
    R120M.BF2_echo_mode.MF7FP1X1.….bin
    R120M.BF2_echo_mode_walk_nearest/      <- ответвление ОТ него, вложено
      R120M.BF2_echo_mode_walk_nearest.MF7FP1X1.….bin
```

Так видно, от чего образ произошёл и с чем его честно сравнивать: соседние по
каталогу образы отличаются одним шагом, а не произвольно. Плоский список из
длинных имён этого не показывает.

## Кто назначает поля версии

`BF` — контролируемое пользователем поле аппаратной совместимости платы и FPGA. Изменять `BF` только в двух случаях:

- пользователь прямо назначил новое значение `BF`;
- пользователь описал фактическое физическое изменение стыка плата–FPGA: перепайку, перенос или обрезание дорожек, смену пинов или разъёма, замену подключённого измерительного чипа либо другое изменение электрического подключения.

Не повышать `BF` только из-за изменения RTL, добавления функции, исправления прошивки или новой сборки. Если `BF` выводится из описанного физического изменения, зафиксировать в сообщении коммита или записи выпуска, какое изменение нарушило прежнюю совместимость.

Поля `MF`, `FP` и `X` агент назначает самостоятельно по фактическим изменениям:

- повысить `MF`, если изменился контракт MCU–FPGA: команды, регистры, сигналы, последовательность обмена или формат данных на этом стыке;
- повысить `FP`, если изменился протокол или формат данных FPGA–PC;
- повысить только `X`, если изменения внутренние и все внешние стыки остались совместимыми;
- если повысилось хотя бы одно поле совместимости, для новой комбинации начать с `X1`.

## Изменение X и сообщение Git-коммита

`X` — целый номер внутренней итерации выпуска внутри конкретной комбинации полей совместимости.

- Если новая выпускаемая версия собрана из изменённых исходников и содержит новый функционал, исправление поведения, изменение RTL, таймингов или другую внутреннюю правку при прежних внешних стыках, увеличить значение `X` на единицу: `Xn → X(n+1)`. Например, после `X9` идёт `X10`.
- Простая повторная сборка того же Git-коммита без изменения исходников не создаёт новую внутреннюю итерацию и не увеличивает `X`.
- Если изменился внешний стык, увеличить номер каждого затронутого поля совместимости (`BF`, `MF`, `FP` для FPGA; `BM`, `MF`, `MP` для MCU), а для новой линии совместимости начать счётчик с `X1`.
- Увеличивать `X` для нового выпуска прошивки, а не для каждого промежуточного Git-коммита, из которого официальный образ не формируется.

До создания исходного коммита, из которого будет собрана прошивка, назначить её новое полное логическое имя. Точное логическое имя обязательно указать в начале заголовка этого Git-коммита:

```text
R120M.BF2MF4FP1X8: add LTDC timeout handling
```

В сообщение коммита включается логическое имя без суффиксов `.git-...` и `.img-...`: собственный hash коммита появляется только после его создания, а SHA-256 образа — только после сборки. Если один исходный коммит намеренно задаёт несколько выпусков, основное имя указать в заголовке, а все остальные полные логические имена перечислить в теле сообщения.

## Имя выданного файла

Формат:

```text
<logical-name>.git-<commit12>.img-<sha256-12>[.uc-<USERCODE>][.dirty][.stale].<STATUS>.<ext>
```

Условный пример; значения `BF/MF/FP/X` определяются конкретным выпуском:

```text
R120M.BF2MF5FP3X7.git-9cb6404af55f.img-25502be6d6c9.uc-00006EAC.BUILDOK.fs
```

Где:

- `git-...` — первые 12 символов Git-коммита исходников;
- `img-...` — первые 12 символов SHA-256 точного выданного файла; это точный идентификатор результата сборки;
- `uc-...` — Gowin `UserCode` из заголовка `.fs`, если доступен;
- `.dirty` — явный признак сборки с отслеживаемыми незакоммиченными изменениями;
- `.stale` — образ старше Git-коммита, которым его пытаются подписать; разрешён только для диагностики;
- полный Git hash и полный SHA-256 хранятся в `.manifest.json`;
- полный SHA-256 также хранится в `.sha256`.

SHA-256 образа нельзя записать внутрь того же образа: запись изменит файл и, следовательно, его SHA-256. Поэтому в FPGA можно заранее встроить Git/build fingerprint или использовать Gowin `UserCode`, а окончательный SHA-256 хранить рядом с файлом.

## Статусы

| Статус | Значение |
|---|---|
| `BUILDOK` | синтез, PnR, генерация образа и обязательные отчёты прошли |
| `HWRUN` | образ загружен и работает, но целевая функция ещё не доказана полностью |
| `HWOK` | требуемая функция подтверждена на целевом железе |

`HWOK` запрещён для dirty-сборки.

## Выпуск

1. Перейти в боевой FPGA-branch, имя которого совпадает с моделью и полем `BF` логического имени: `R120M.BF1` для TDC7201 или `R120M.BF2` для LTDC.
2. Убедиться, что `origin` указывает на `ak-tech-electronics/ToF-LIDAR-FPGA`.
3. Определить полное логическое имя нового выпуска. При прежних внешних стыках и новом функционале увеличить `X` на единицу; при изменении стыка повысить соответствующее поле совместимости и начать новую линию с `X1`.
4. Закоммитить исходники и изменения подмодулей. Начать заголовок исходного коммита с точного логического имени выпуска.
5. Собрать проект из чистого текущего `HEAD` и проверить отчёты согласно `fpga-dev` и `gowin-fpga`.
6. Упаковать артефакт:

```powershell
.\docs\skills\firmware-release-naming\scripts\New-FirmwareArtifact.ps1 `
  -LogicalName R120M.BF2MF4FP1X8 `
  -Artifact .\impl\pnr\R120M_LTDC_MSOP.fs `
  -OutputDirectory C:\firmware\releases `
  -Status BUILDOK `
  -TopModule R120M_ltdc_msop_brd_ifm `
  -Target GW2A-LV18PG256C8I7
```

7. Сверить выданный SHA-256 с `.sha256`.
8. После аппаратной проверки повторно упаковать или оформить запись со статусом `HWOK`.

Не коммитить сгенерированные `.fs`/`.bin` только ради хранения релиза. При необходимости коммитить выбранный manifest, а двоичный файл хранить в принятом хранилище релизов.

## Публикация на сервер

Выкладывать прошивки на общий сервер только по явному запросу пользователя.

На сервер разрешено копировать только файлы прошивки:

- `.fs`;
- `.bin`.

Не копировать на сервер `.manifest.json`, `.sha256`, `.rpt.txt`, timing-отчёты, логи, архивы и любые другие сопроводительные файлы. Manifest и контрольная сумма создаются и хранятся локально для трассируемости выпуска; это не серверные артефакты.

**На сервере разрешено ТОЛЬКО добавлять.** Не удалять, не перезаписывать и не
переименовывать файлы прошивок — ни чужие, ни свои, ни только что выложенные,
ни заведомо ошибочные. Каталог прошивок общий: по нему могут идти чужие замеры,
на него могут ссылаться отчёты и записи стенда, и исчезнувший образ ломает
чужую работу молча. Ошибочный выпуск выводится из обращения НОВЫМ выпуском с
увеличенным `X` и записью в manifest, а не удалением старого файла.

Если кажется, что старый образ обязательно надо убрать (например, два соседних
имени легко перепутать на стенде), — сказать об этом пользователю и оставить
решение ему. Удалять можно только по явной просьбе.

## Аварийный dirty-режим

`-AllowDirty` нужен только для диагностических образов. Скрипт добавит `.dirty`, запишет статус Git и hash diff в manifest.

`-AllowArtifactOlderThanCommit` нужен, если требуется изучить старый образ. Скрипт добавит `.stale` и запишет разницу времени между коммитом и файлом.

Dirty- или stale-образ не может иметь статус `HWOK`.
