# Obsidian Style

Use this reference before creating or editing Obsidian notes.

## Writing

- Write in Russian by default.
- Keep English technical terms next to Russian terms when useful.
- Use concise Markdown that is useful as a note, not chat transcript prose.
- Build explanations as a smooth narrative: motivate each new object, operation, or symbol before it appears, so nothing shows up "ни с того ни с сего" (out of nowhere). Do not start a paragraph as if answering an implicit question the user/reader did not ask; first state the local task to solve (for example, "далее нужно решить..."), what its solution requires, and only then introduce the definition, equation, or physical fact that makes the next object necessary. When a non-obvious step enters a derivation - e.g. "умножение поля на $\varepsilon(x)$", a new matrix, a substitution - first give one or two sentences on where it comes from (which equation, definition, or physical fact forces it), then perform the step. Lead the reader from the familiar to the new; prefer a short bridging sentence/paragraph over an abrupt jump, even in terse term notes (explicit user requirement, 2026-07-03).
- Unfold that narrative in explicit sequential steps with signpost words - «сначала … затем … далее … получаем … вывод …» (or equivalents) - so the reader sees the order and how each step follows from the previous one, not a pile of loose paragraphs. Each step should visibly hand off to the next (from a definition, to the equation it enters, to the consequence). Do NOT use meta openers inside notes such as «совсем издалека», «что вообще значит …», «если совсем просто»: drop the meta framing and start the actual step (e.g. «Сначала — откуда возникает …»). The user asked for sequential, signposted exposition and explicitly rejected the «совсем издалека» framing in a note (explicit user requirement, 2026-07-03).
- Do not repeat the note filename as a heading at any level, including `####`: Obsidian already shows the file title above the note, so the body must start with the definition or introductory text.
- After a short label line ending with `:`, place the following paragraph, list, or code block on the next line without an empty line. Example: `Полезные ключи:` followed immediately by `- ...`.
- A Markdown table is the ONE exception to the "no empty line" rules above and below: it MUST be preceded by a blank line, unless it starts directly under a `####` heading. GFM tables cannot interrupt a paragraph, so a table glued to a lead-in line ending with `:` is absorbed into that paragraph and renders as literal text full of `|` characters — the note looks broken to the reader while the source looks perfectly correct, which is why this slips through self-review. Write the lead-in `Карта сокетов ...:`, then a blank line, then the header row. A table right after a `####` heading needs no blank line, because the heading already closes the block; the same holds after a closing ``` fence or a closing `$$`. Do not rely on memory here — `Test-Note.ps1` checks it (user correction, 2026-08-13, after a port-map table rendered as raw pipes).
- Use `####` for topical section headings in scientific and technical Obsidian notes, including small standalone term notes. Do not use `#`, `##`, or `###`; the filename already supplies the note title, so a `#` heading duplicates it.
- Write a topical section header as a `#### ` heading, not a bare bold-less label line. Multi-sentence sections - `Физический смысл`, `Идея`, `Границы применимости`, `Как решается`, `Связь с расчётом`, `Связанные заметки` and the like - get `#### ` (drop the trailing colon). This applies to small term notes too, not only large structured notes. Reserve a bare label line ending with `:` for a short notation or enumeration block tied to what immediately follows: `Где:` after a formula, `Полезные ключи:` before a list, or a one-line lead-in that directly precedes a display formula.
- Do not leave an empty line after a heading; place the following paragraph, list, or code block on the next line directly under the heading, the same as after a label line.
- Do not leave an empty line between a display formula and its `Где:` notation block: `Где:` goes on the next line immediately after the closing `$$` (explicit user requirement, 2026-07-03). When touching an existing note, remove such blank lines in the edited fragments.
- Use LaTeX math syntax for formulas, not fenced code blocks. Obsidian renders it with MathJax, so the engine is not KaTeX; write plain LaTeX math.
- For inline formulas in Obsidian notes, use `$...$`, not `\(...\)`: in this vault `\(...\)` can remain visible in rendered text instead of displaying as math. Use `$$...$$` for display equations.
- Do not embed bare math operators like `$\le$`, `$\ge$`, `$\sim$` glued into prose (e.g. `($\le$400 нм)` or `$P\ge$half-max`) - such fragments render unreliably in Obsidian (user-confirmed). Either use the Unicode character in plain text (`(≤400 нм)`, `P ≥ half-max`) or put the whole expression inside one inline formula (`$\lambda \le 400$ нм`).
- After formulas that introduce or combine symbols, explain notation with a separate, non-indented `Где:` block followed immediately by non-indented bullet items, for example `Где:` then `- $\beta$ - ...` and `- $k_0$ - ...`. Do not indent `Где:` or its bullets under a previous list item, because Obsidian will render them as nested bullets.
- Each `Где:` block must be locally complete for the immediately preceding formula and any coefficient-definition line directly attached to it. List every symbol, index, parameter, and coefficient that the reader needs to interpret that local formula, even if the same symbol was already defined earlier in the note or in a previous `Где:` block. Do not omit repeated symbols to avoid duplication: if the same symbol appears in ten formulas, repeat its local meaning in ten corresponding `Где:` blocks. Reuse the same concise wording and links when appropriate. For example, if the prose introduces `$\alpha=1/K$` before a displayed formula written through `$K$`, the following `Где:` block still includes both `$\alpha$` and `$K$` (explicit user requirement, 2026-07-04).
- Never fold formula notation into an inline prose sentence such as "где $X$ — ..., $Y$ — ...". Always use the `Где:` block with exactly one symbol per bullet, even for just two or three symbols, in the form `- $symbol$ - description` (symbol, space-hyphen-space, then the meaning). Link every symbol that has a term note, for example `- $\mathbf{P}$ - [[материальная поляризация среды (P)]]` and `- $\varepsilon_0$ - [[диэлектрическая проницаемость свободного пространства (вакуума)]]`.
- Do not denote a dimensionless count with a symbol that reads as a dimensional quantity. A counter reading (clock ticks, samples, periods) written as `$T$` makes an expression such as `$T\,t_{clk}$` read as "time × time", so the reader stops on an apparent dimensional error even though the formula is right, and stating "тактов" in the `Где:` block does not repair it — the symbol fights the unit. Use `$N$` with a qualifying subscript for counts (`$N_{\text{ребра}}$`, `$N_{\tau}$`), reserve `$T$`/`$\tau$` for seconds, and write the bridge explicitly as its own formula (`$T = N\,t_{clk}$`) before the count first appears in a fraction. When a derivation mixes both worlds, add one sentence naming what the denominator physically is. Fix such a symbol everywhere in the note at once — display formulas, `Где:` blocks, table headers, and running prose — not only in the formula the reader flagged (user correction, 2026-08-06, angular-lead derivation where `$T_{\text{ребра}}\,t_{clk}$` looked like a mistake).

- Keep genres separate: an analytical note states the model, the governing relation, the chain of limits, and what follows from them; a defect of the current implementation does not belong in it. A bug is a property of today's code, not of the physics, so mixing the two makes the analytical note expire with the next fix and buries the reusable part under incident history. Put defects in the project's defect/session record and, when the analysis genuinely depends on one, state the constraint in engineering terms ("рабочий диапазон — шаг не мельче 0.20°") without the incident narrative. User correction 2026-08-13, on a note deriving the lidar's maximum scan rate.

- Strip invisible characters from anything pasted in from a rendered web page. Zero-width spaces, word joiners, soft hyphens and directional marks survive copy-paste, show the reader nothing, and break things silently: a `U+200B` inside `$...$` makes the formula stop matching any search, and one after a `####` marker breaks the `[[#Heading]]` anchors this vault relies on. The usual source is copying MathJax-rendered formulas from a page — the giveaway is doubled symbol names such as `neffneff` next to a no-break space. `Test-Note.ps1` fails Strict on them and reports exotic spaces separately, since a non-breaking space can be deliberate in Russian typography. Do not hand-edit them out — they are invisible in the editor, so a manual pass misses some; run `scripts/Repair-NoteInvisibles.ps1 -Apply` and re-validate. Sweep the whole vault after any batch of docx/PDF conversions: the 2026-08-16 sweep healed 294 characters across 37 notes, and soft hyphens from converted lectures outnumbered the web-paste zero-width spaces.

## Visuals

- Visuals are welcome, not optional decoration: when a diagram, matplotlib plot, or schematic makes a concept clearer than prose (профили полей, ряды/частичные суммы, огибающие, геометрия структуры, сравнение кривых, ход алгоритма), generate one and embed it by default in explanation and reproduction notes. Offer it proactively; the user has confirmed illustrations are appreciated (explicit user requirement, 2026-07-03).
- A note without a single illustration is the exception, not the norm. Before finishing any explanation, term, reproduction, or paper note, ask explicitly "which picture belongs here", and only leave the note text-only when the answer is honestly "none" (explicit user requirement, 2026-08-20). Term notes count: a definition is usually clearer with one field map, one dependence, or one geometry sketch.
- **The illustration check is retroactive, not a creation-time gate.** Phrased as "before finishing a note", the rule above silently exempts every note that already exists, so a note written earlier stays illustration-free forever and the gap surfaces only when the user says the note is hard to grasp. Whenever you open an existing explanation, term, reproduction, or paper note for any reason — answering a question about it, fixing a link, editing one paragraph — run the same "which picture belongs here" check on the whole note and add what is missing in the same task, not as a follow-up suggestion. The strongest signals are a comparison table with no chart, prose describing field profiles or geometry with no picture, and two opposing limits argued only in words (user correction, 2026-08-21: the plasmonic-photonic coupling term note carried a three-scheme comparison table and two opposite physical limits without a single figure).
- **Search the vault for an existing figure first.** Earlier work has usually already produced the picture this note needs, and reusing it costs nothing, keeps the vault visually consistent, and links the two notes together implicitly. Look before generating: `Glob` for `*.png` under the topic's folders, the `attachments/` and `*_media/` folders next to related notes, and any `CODEX/` calculation folders; also check what related notes already embed. Only when the vault has nothing suitable, generate the figure yourself, crop it from the source PDF, or — as the last resort — look for one on the web (explicit user requirement, 2026-08-20).
- When taking a figure from the web, download it into the vault rather than hotlinking a URL: an external link rots and does not sync with the vault. Put the file in the note's media/attachments folder, and in the caption state the source and, when it matters, the licence. Do not present a borrowed figure as your own calculation.
- **A reused figure must be captioned for its own parameters, not the note's.** A picture pulled from another vault note was almost always computed for a different structure, and silently placing it under the current note's numbers is a factual error. Say in the caption which geometry and material set it belongs to, and when the two differ, make that a point rather than hiding it: two independent structures showing the same qualitative behaviour is stronger evidence than one (2026-08-20: the LR-SPP term note reuses `Si | Au 20 nm | Si` parity and thickness-sweep figures alongside a 3D scene computed for `Au 14 nm` in a polymer, and says so).
- Put generated figures in the note's `<note name>_media/` folder and keep the small generating script (`.py`) beside the PNG for reproducibility. Embed with a bare `![[figure.png|620]]` (add width) and follow it immediately with a one-paragraph caption explaining what each panel shows and how it ties to the note's formulas.
- **Open every generated PNG and read it against a checklist before embedding it.** Looking at the image is necessary but not sufficient: a glance catches gross layout breakage and misses defects that make the figure argue the wrong thing. Run the list, item by item, on each panel (user correction, 28.08.2026 — a two-panel interference figure was embedded with one curve invisible and another unreadable, after the PNG had been opened and looked at):
    - **Coincident series.** If two plotted quantities are mathematically equal, the one drawn second hides the first completely and the reader sees a single curve where the point is that there are two. Separate them by a small deliberate offset, state that offset on the figure and in the caption, and give them different colours — a dash pattern alone is not enough when the curves are identical.
    - **A constant-zero result drawn on the axis line.** A sum that cancels reads as the axis, not as data: the reader sees nothing where the whole point is that the value is zero. Remove or lighten the axis line, draw the result noticeably thicker, and annotate it in words («сумма равна нулю на всей длине»).
    - **Every legend entry must be findable in the plot**, and every element named in the caption must be visually distinguishable. Walk the legend and the caption and point at each item in the picture; anything you cannot point at is a defect.
    - **Text collisions**: labels over curves, labels over each other, legend over data, axis labels clipped at the edge. Check the corners and the peaks of the curves, which is where annotations usually land.
    - **The claim in the caption must be visible in the figure.** If the caption says the amplitude doubles, the doubling has to be measurable by eye against the components.
  Re-render and re-read after every fix; a fix in the plotting code routinely moves a label onto a curve that was clear before.
- Prefer a simple, self-contained matplotlib script (normalized/illustrative parameters are fine) over pixel-perfect figures; state in the caption when the illustration is normalized or simplified versus the real calculation. Cyrillic labels render fine with the default DejaVu Sans font.
- When the note already states a number, prefer a figure that **recomputes that number independently** over one that merely redraws it. The cost is usually small — a self-contained solver for the reduced (planar, 1D, analytic) version of the problem is under a hundred lines — and the payoff is double: the picture explains the claim and audits it at the same time, and a mismatch is caught at the moment the figure is drawn rather than by a reviewer. Validate the little solver against a closed form before trusting its picture, and say in the caption what it was checked against and that it reproduces the mechanism rather than the source's exact numbers (2026-08-21: a planar transfer-matrix script written for the coupling term note reproduced both the vault's 99.89 % matched-mode overlap and Abadía's ~4 % interface reflection from an independent structure).
- Every textual reference to a visual must be backed by that visual actually present in the note. Whenever the prose says «на кривой … видно», «на рисунке», «на графике», «см. схему», «as the curve shows», names an axis or a plotted dependence like `$T(L)$`, or otherwise points the reader at a picture, the corresponding image MUST be embedded right there — a `![[...]]` embed on its own line with a caption. A sentence that describes what a figure shows without the figure being in the note is a defect: the reader is told to look at something that does not exist. This was an explicit user correction (2026-08-18: «На кривой $T_{In\,the\,mode}(L_{taper})$ видны осцилляции» appeared with no curve in the note). When you write such a phrase, either embed the figure or rewrite the sentence so it no longer refers to a picture (state the fact directly, e.g. «зависимость немонотонна из-за резонанса Фабри–Перо»).
- Source the referenced figure honestly. For a paper/reproduction note, prefer the real figure extracted from the source PDF (crop the page region and save it to the note's media folder), and cite it as the source's figure in the caption. If the source figure cannot be extracted, reproduce it with a self-contained matplotlib script beside the PNG and label the caption as a reconstruction/illustration, not the original. Never leave the reference dangling.

## Links

- Use Obsidian links for local concepts: `[[FCS]]`, `[[CRC_32|CRC-32]]`.
- Use the shortest Obsidian link path that resolves unambiguously, matching Obsidian's "Shortest path when possible" behavior. Prefer `[[Note title]]` or `[[Note title|alias]]`; include folders only when needed to disambiguate duplicate note names, and avoid full vault-relative paths unless no shorter stable link works.
- The same shortest-path rule covers attachment embeds (images, PDFs): prefer a bare `![[file.png]]` when the filename is unique in the vault, and add the minimal folder path only to disambiguate a duplicate name. Never use parent-relative `../` paths in links or embeds — under Obsidian's default "Shortest path when possible" link format they resolve unreliably, so the embed silently breaks (shows a broken-image placeholder) even though the file exists on disk.
- Reference a paper or source PDF that lives in the vault with an Obsidian wikilink, never a plain path string in backticks or prose. Link the paper note `[[Paper note]]` when one exists; otherwise link the file itself with an aliased wikilink `[[YYYY - Author - Short Title - doi_....pdf|readable alias]]` — a link, not an `![[...]]` embed (embedding renders the whole PDF inline). Filenames are unique, so the bare-name wikilink resolves under shortest-path — do not write the containing folder path (`Статьи Лерера (PDF)/...` as a backtick string is wrong; `[[...pdf|Лерер 2012]]` is right). This keeps the citation clickable and lets backlinks track which notes cite the source; the `literature_pdfs/` manifest already follows this.
- When writing formula notation blocks such as `Где:`, check whether explained terms already have notes in the vault and link them in the bullet text; for example use `[[Propagation constant (постоянная распространения, продольное волновое число)|постоянная распространения]]` instead of plain "постоянная распространения".
- Before finalizing any note, actively search the vault (Glob/Grep by the term's word and by likely note-title fragments) for an existing term note for EVERY named physical/mathematical quantity, not only the headline ones. This explicitly includes secondary or intermediate symbols introduced mid-derivation - e.g. $k_z$ (продольное/longitudinal wavenumber), $k_x$ (поперечное), $\kappa$ (коэффициент затухания), $k_0$, $n$, $\beta$ - which are easy to leave unlinked. Do not assume "no note exists" from memory: run the search, and if a matching note is found, link it at each occurrence in prose and `Где:` blocks. The user has flagged missed links to existing notes (e.g. `[[Propagation constant (постоянная распространения, продольное волновое число)]]`) as an error to avoid (explicit user requirement, 2026-07-03).
- Audit enumerations separately. In every phrase of the form «X, Y и Z», inspect each noun phrase that names a physical quantity, mathematical operation, criterion, method, material, phenomenon, or mode property. Search for an exact standalone term note for every item; link every item, and create the missing exact term notes before finishing. Do not consider an enumeration linked merely because its first or main term has a wikilink. Apply the same check to comma-separated criteria in prose, bullets, captions, table cells, and `Где:` blocks (explicit user correction, 2026-07-11).
- If a term has a common display alias, use `[[Note title|alias]]`.
- Do not put LaTeX/math markup (`$...$` or `$$...$$`) inside an aliased Obsidian wikilink display text. Obsidian does NOT render math inside alias text - it stays literal and shows the raw `$\chi^{(3)}$` / `$$...$$` to the reader (user-confirmed 2026-07-07, after `[[Note|феноменологическую $\chi^{(3)}$-ветку]]` rendered as literal `$\chi^{(3)}$`). Two fixes: (a) write the alias in plain Unicode without any `$`, e.g. `[[Феноменологическая χ(3)-ветка ...|феноменологическую χ⁽³⁾-ветку]]` or `[[L_pi ...|$L_\pi$]]` → `[[L_pi ...|Lπ]]`; or (b) keep the formula outside the link, e.g. `$L_\pi$ - длина $\pi$-фазового сдвига, см. [[L_pi (длина pi-фазового сдвига)]]`. In particular, never write `[[Коэффициент отражения (Г) по напряжению (S11)|$S_{11}$]]`; use the plain-Unicode alias `[[Коэффициент отражения (Г) по напряжению (S11)|S₁₁]]` or keep `$S_{11}$` outside the link. The same applies to inline `$...$` in prose that gets wrapped into an alias.
- Do not put aliased Obsidian wikilinks `[[Note title|alias]]` (or embeds `![[img|width]]`) inside Markdown table cells: the `|` is parsed as a column separator, the row gains a phantom column, and Obsidian's table editor then reflows the whole table around the torn link — the damage looks like a "randomly" restructured table, not like a link problem. In tables, use plain text in the cell and add the Obsidian link in surrounding prose, or use an aliasless `[[Note title]]` link if the full title is acceptable. Do not rely on memory here — `Test-Note.ps1` flags wikilinks containing `|` in table rows (violated 2026-08-13: `[[Энкодер (encoder)|энкодера]]` in an address-map table split the row and Obsidian rewrote the table with an extra empty column; the validator check was added after that user correction).
- Do not duplicate standalone term-note explanations inside working notes, paper notes, method notes, or formula notation blocks. If a term already has a note, link it and keep only the local role needed for the current formula or argument.
- When a new term note was created because of a specific source note, link the term naturally from that source note if the location is obvious.
- Do not add meta-comments inside notes such as "to avoid duplication"; just link naturally.
- Linking direction (one-line rule): a specific note always links up to its broader concept with exactly one inline link (for example RC-цепь → `[[Теория цепей]]`, reading as "частный случай ..."); a general note links down to specific notes only when it genuinely acts as a hub/MOC and the list is curated deliberately, never exhaustively by hand, because Obsidian backlinks already expose the children. When adding only one direction, prefer specific→general.
- Distinguish three link roles so direction is unambiguous: hierarchical (specific→general, "частный случай"), structural (hub/MOC → its curated children), and contextual/definition (a note that *uses* a term links to that term's standalone term-note). A definition link is usage→definition (lateral), not a taxonomic up-link: linking `[[Реактивное сопротивление]]` from RC-цепь means RC-цепь uses the term, not that it is a kind of it. This realizes single source of truth — the definition lives once in the term-note and everything else links to it, while backlinks collect the usages.
- When a term with a standalone term note appears multiple times in the same note's running prose, link every occurrence, not only the first. Do not apply a "link once per note is enough" convention: repeat `[[Note title|alias]]` (or the bare term as an alias, e.g. `[[Локализованный поверхностный плазмонный резонанс (LSPR)|ЛППР]]`) at each place the term's word or abbreviation appears, even ten times in one note. This was an explicit user correction after an abbreviation (`ЛППР`) was left unlinked on a later occurrence in a note that had already linked it once earlier.

## Term Notes

- Never put a colon in a note filename. This vault lives on Windows, where `:` is reserved, so `Write` fails with `EINVAL: invalid argument, rename ...` and the note is silently not created; the same applies to `\ / * ? " < > |`. Use an em dash instead: `Фиктивный параллелизм — несколько задач за одним мьютексом.md`, not `Фиктивный параллелизм: ...`. Decide this before writing, because the failure surfaces only at write time and any wikilink already authored to the colon title then has to be fixed too (hit 2026-08-13).
- Name new standalone term notes for searchability as `Primary Russian term (Russian synonym, English term).md` when an established synonym and English equivalent exist. For example, use `Промежуточная таблица (связующая таблица, junction table).md` instead of `Промежуточная таблица.md`. Include only useful established forms that the user is likely to search; if a term has no meaningful synonym or English equivalent, keep the shorter title (explicit user requirement, 2026-07-21).
- Start with a short definition.
- Add physical or engineering meaning.
- Add key formula, packet field, geometry, applicability, or limitation when relevant.
- Keep small standalone term notes focused; link out for deeper context.
- If only a related or narrower note exists for a term (for example roots, coefficients, examples, or a method that uses the term), create the exact standalone term note anyway and link the related note to it. Do not use an alias to a narrower note as the definition target for the broader term (explicit user requirement, 2026-07-04).

## Paper Notes

- Any note that is a conspect, analysis, reproduction, translation, or full-text conversion of a specific article or document MUST link its source with an Obsidian `[[wikilink]]` to that file, near the top of the note (a `Разбор источника:`/`Source:` lead line). Link the source file itself `[[YYYY - Author - Title.pdf|readable alias]]`; if a separate analysis/paper note exists, cross-link it too. Never leave the source as a bare path string in backticks or prose - a backtick path is not a backlink, so the source shows no incoming links even though the whole study is built on it. This applies to script-generated conversions as well: fix the generator to emit the wikilink, not a path (explicit user requirement, 2026-07-09).
- In notes that analyze or reproduce a paper, never cite the paper's internals bare: "формула (1)", "рис. 2", "п. 3" must say whose they are - "формула (1) статьи [[paper-note]]", "рис. 2 статьи" - because the note has its own figures/formulas and bare numbers are ambiguous. Referencing the source paper's own formulas, paragraphs, and headings is allowed and encouraged; when the note reproduces that formula in its own section, also point to that section ("воспроизведена в п. 2.1").
- Apply that qualification at EVERY mention, not only the first or the heading (explicit user requirement): each "формула (1) статьи" in body text, figure captions, and Где-blocks carries the `[[paper-note]]` link plus a same-note anchor `[[#Section|п. 2.1]]` to where the formula is reproduced. A reader landing mid-note must be one click away from both the source and the reproduced formula; text baked inside generated scheme images cannot link, so the caption under the image must carry the links instead.
- Reproduction/method notes need a geometry/model schematic per modeling level (what exactly is being solved: layers, periods, sizes, incidence) - a reader should not have to reconstruct the solved structure from prose; generate a simple matplotlib scheme into the note's media folder if the source has none.
- Never leave bare internal cross-references like "см. п. 3.3", "та же геометрия, что выше", "см. Схему 3" - they force the reader to scroll-hunt (explicit user requirement). Make them clickable: same-note heading anchor `[[#3.3 Full heading text|п. 3.3]]`, or link/re-embed the referenced figure (a small `![[scheme.png|420]]` copy on its own line is fine). Exception: inside Markdown table cells keep plain text (aliased links break tables). For heading anchors to work, keep headings free of wikilinks - link terms in the body near the heading instead of inside it.

## Mermaid Diagrams

- In Mermaid labels for Obsidian, never start label text with a Markdown list marker - ordered `1.`/`1)` or unordered `-`/`*`/`+`: Mermaid parses label text as Markdown, and Obsidian renders the whole node as `Unsupported markdown: list` instead of the text (violated again 2026-07-29 on the lidar startup diagram despite this rule - rely on the validator, not memory). The rule applies to every fragment that begins a rendered line: the label start, the text right after each `<br/>`, and edge labels (`-- "..." -->`, `|...|`), not only node labels. Use wording such as `Шаг 1 - ...` instead of `1. ...`.
- `Test-Note.ps1` flags Markdown list markers inside ```mermaid fences (strict mode fails with the other style checks), so always run it after creating or editing a note that contains a Mermaid diagram.
- Make flowchart edges clearly visible: start every ```mermaid flowchart with the directive line `%%{init: {"themeVariables": {"lineColor": "#999999"}} }%%` (before `flowchart TD`; `lineColor` recolors both the edge lines and the arrowheads) and end the block with `linkStyle default stroke-width:3px` on its own line. Width alone is not enough: 3px edges in the default dark stroke are still nearly invisible on the Obsidian dark theme, so both the width and the contrast color are required (explicit user request, 2026-07-29).

## Safety

- Do not move or rename notes unless explicitly asked.
- Do not create broad folder restructures during a focused answer.
